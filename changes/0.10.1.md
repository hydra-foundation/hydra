Paging is no longer something only the admin can do. An API controller can read `page` and `per_page` with `Paging`, hold one page of results in `Paginated`, and answer with `Responder::paginated()`, which returns `data`, `meta`, relative `links` and a `Link` header. It keeps the same guard against a page number big enough to force a full table scan. The admin's list screens are now built on these, and a list asked for a page past its end shows its last page instead of an empty table.

This is a patch release because nothing was removed or changed shape. `Criteria`, `Page` and `SourceInterface` read as before, so an app upgrades with `composer update` inside `^0.10`.

## The admin

- A list screen asked for a page past its end (`?page=9994` on a list with 13
  pages) now shows its last page instead of "No results". This used to happen
  only after a delete emptied the last page.

## HTTP

- Paging a list outside the admin. `Paging::fromQuery($query, 20, 100)` reads
  `page` and `per_page`, clamps both, and caps the page at `Paging::MAX_PAGE` so
  a typed URL can't turn into a full table scan. `Paginated` holds one page of
  results. `Responder::paginated()` renders it as `data`, `meta` and relative
  `links`, plus an RFC 8288 `Link` header.

  The admin's `Criteria` and `Page` are now built on these, and nothing changes
  for a module. `Criteria::MAX_PAGE` still works, as an alias of
  `Paging::MAX_PAGE`.

<p>Until this release the framework repository had no end&#8209;to&#8209;end test at all. Every flow that booted a real application and drove a real request lived in the skeleton, whose CI installs from a committed lock &mdash; so the only tests proving the pipeline works were testing the <em>previously released</em> packages, and a kernel change that broke boot was discoverable after the tag rather than before it. The framework now boots an application of its own. Everything here is additive &mdash; <code>bin/api-surface.php</code> reports the tag clean &mdash; which is why it is a patch, even though it publishes four classes into a namespace that had only ever held abstract cases. Framework suite 1219 tests and 2618 assertions to 1295 and 2941; the skeleton 319 and 956 to 246 and 673, which is the same work counted in a different repository.</p>

<h3>Four test doubles that ship</h3>

<p>Every application testing against Hydra was writing the same four providers by hand, because the framework offered no way to hand them over. <code>src/Testing</code> is that way &mdash; it is inside <code>autoload</code>, where a dependency&rsquo;s <code>autoload-dev</code> is not &mdash; and it already held the published contract cases for exactly this reason. It now holds doubles too.</p>

<p>The three providers register ahead of the ones they replace, which is all a harness has to know. Each is generic in the strict sense &mdash; nothing in it knows which application it is standing in &mdash; and that is the test for whether something belongs here rather than in a project&rsquo;s own <code>tests/Support</code>.</p>

<p><code>CapturingLogger</code> is one class where there were two. A test driving real requests wants the pipeline&rsquo;s log line kept out of PHPUnit&rsquo;s output; a test about the event chain wants to read the records back and say which ones fired. Holding them in memory answers both, so the quiet logger that used to do the first job is gone rather than moved. It offers <code>records()</code>, <code>messages()</code>, <code>has()</code>, <code>clear()</code>, and <code>firstWith()</code>, which throws naming every message that <em>was</em> logged &mdash; a missing record is the common assertion, and &ldquo;no such record&rdquo; on its own sends you back to add a dump.</p>

<div class="note warn">
  <span class="label">The flag that could not see it</span>
  <p><code>beStrictAboutOutputDuringTests</code> never caught the stray log line, for four releases. A logger holding a stream writes to the descriptor directly and never passes through output buffering, so the flag has nothing to observe. Worth knowing about its reach: it catches what a test <em>echoes</em>, not what a test causes to be written.</p>
</div>

<h3>The fixture application</h3>

<p><code>hydra/tests/fixture</code> is a small, complete application the framework owns: controllers, views, a one&#8209;table SQLite schema, an admin with two modules, and the global stack eleven middleware deep. It exists because <code>app/</code> was doing two jobs that pull apart. A fixture wants hostile routes, every middleware ordering and the failure paths; a skeleton wants to stay minimal and exemplary, because it is what <code>create-project</code> hands a user to read. The skeleton goes back to the second job only.</p>

<p><code>Fixture::boot()</code> is the harness, and it is the part that earned the directory. The flows were each hand&#8209;rolling a copy of it: eleven providers in a fixed order, a logger that has to be bound <em>before</em> <code>boot()</code> or the listeners are built against whatever was bound first and hear nothing, and a hash cost lowered or the suite spends its run inside bcrypt. Every flow that had one of those subtly wrong was still green, and testing something slightly different from the others.</p>

<p>The cost is a second application to keep booting, taken knowingly. It buys one thing the skeleton could not: the framework can point its own failure paths at itself without any of that landing in code someone is meant to learn from.</p>

<h3>Six flows changed repository</h3>

<p><code>RequestLifecycle</code>, <code>AuthFlow</code>, <code>AuthEvents</code>, <code>RateLimit</code>, <code>AdminAuthorization</code> and <code>AdminModule</code> now run in the framework, against the fixture &mdash; 73 tests, ported method for method. What they assert is the pipeline, the guard, the limiter and the admin&rsquo;s three htmx depths, none of which was ever about the skeleton.</p>

<p><code>Activity</code>, <code>Audit</code> and <code>Settings</code> stayed. Each is over application code &mdash; a middleware, a listener, a preferences module &mdash; and moving them would have meant reimplementing the skeleton inside the fixture in order to test the skeleton.</p>

<p>The two suites together went from 1538 tests to 1541. The seventy&#8209;three that moved are the same seventy&#8209;three; the three that are new are regression tests for the two gate fixes below.</p>

<h3>api-surface could not see a concrete double</h3>

<p>The release gate reads <code>src/Testing</code> under an inverted rule: a consumer <em>extends</em> a contract case, so its abstract methods are the part that can break them and its test methods are noise that would churn the listing on every edit. That rule was written when the directory held nothing but cases, and it keyed on the path.</p>

<p>A concrete double is the opposite &mdash; a consumer calls it &mdash; so <code>CapturingLogger</code> entered the surface as a bare class name with none of its public methods recorded, and renaming any of them would have shipped as a patch. The rule is abstractness now rather than the directory. The regression test is the one new test in this release.</p>

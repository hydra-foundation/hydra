<p><a href="0.5.4.html">0.5.4</a> ended by naming what <code>TableSource</code> still could not check &mdash; a module field marked <code>filterable</code> on a key its source does not list, which widens a narrowed request to the whole table in silence &mdash; and concluded that it needed a test per module. This release replaces that conclusion with a command, and then removes the tests it was written to replace. Everything here is additive, which is why it is a patch: <code>bin/api-surface.php</code> reports nothing taken away. Framework suite 1206 tests and 2544 assertions to 1219 and 2618; the skeleton 300 and 897 to 319 and 956.</p>

<h3>admin:check</h3>

<p><code>php bin/console admin:check</code> reads every registered module against the source it names and reports each field the source does not offer. It checks the four lists separately &mdash; a column can be selectable without being sortable &mdash; and the module&rsquo;s <code>defaultSort</code> along with them, since a default sort on a column the source will not sort by fails at the first page load rather than at the first click.</p>

<p>It reads a source through <a href="/docs/admin.html#describe"><code>DescribesColumnsInterface</code></a>, one method returning a <code>SourceDescription</code>. <code>TableSource</code> implements it by handing back the declaration it was built with. Nothing at runtime reads it: the SQL is built from the same properties directly and a screen never asks a source what it is, so this exists for the check and for a test that wants to state the pairing rather than assume it.</p>

<div class="note">
  <span class="label">Why it is not in composer qa</span>
  <p>It needs a live database, and <code>qa</code> runs on a checkout that may have none. The skeleton closes that with <code>tests/Unit/AdminModulePairingTest.php</code>, which runs the command over the real module list against the SQLite test schema &mdash; so the pairing is checked on every suite run, not on every release. A second case in that test fails when a source cannot be described at all, because the command reports an unresolvable source as &ldquo;not describable&rdquo; and a silent skip would read as a pass.</p>
</div>

<p>A source that offers more than the module names is not a finding. The module is the narrower contract by design, and reporting the difference would make every source look wrong.</p>

<h3>Six generators</h3>

<p>The skeleton gained a <code>make:</code> family that reads the live table and writes code against its actual columns, rather than a template with placeholders to fill in.</p>

<div class="tw">
<table>
  <thead><tr><th>Command</th><th>Writes</th></tr></thead>
  <tbody>
    <tr><td><code>make:source</code></td><td>An admin source, columns declared from the table.</td></tr>
    <tr><td><code>make:module</code></td><td>A module definition with a field per column.</td></tr>
    <tr><td><code>make:entity</code></td><td>A readonly entity, one promoted property per column.</td></tr>
    <tr><td><code>make:repository</code></td><td>A repository with its reads spelled out.</td></tr>
    <tr><td><code>make:listener</code></td><td>A listener for an admin event.</td></tr>
    <tr><td><code>make:migration</code></td><td>An empty timestamped <code>.sql</code> file. (Framework, and older than this release.)</td></tr>
  </tbody>
</table>
</div>

<p>Three decisions are shared by all of them, in <code>MakeFromTableCommand</code>. Columns come from the schema in schema order, so the generated field order matches the table rather than an alphabetical accident. A column whose name looks like a secret &mdash; a hash, a token &mdash; is read but never written, so a generated form cannot offer to edit a password hash. And reads are named rather than <code>SELECT *</code>, so a column a later migration adds does not arrive in every caller the moment it runs.</p>

<p>What they do not do is relieve you of <a href="/docs/module.html">the checklist</a>. A generated module and a generated source agree on the first day and drift on any day after, which is the gap <code>admin:check</code> now covers.</p>

<h3>Removed: activity:seed</h3>

<p>The skeleton&rsquo;s <code>activity:seed</code> command is gone. It wrote fabricated rows into a table whose entire purpose is to record what actually happened, and an audit trail with invented entries in it is worse than an empty one &mdash; the emptiness is at least true. Nothing in the framework changed; this is a command the skeleton no longer ships.</p>

<h3>./hydra passes its arguments through</h3>

<p>The skeleton&rsquo;s <code>./hydra</code> was <code>./bin/exec bin/console</code> with no <code>"$@"</code>, so it swallowed everything after it and could only ever print the command list. It takes arguments now &mdash; <code>./hydra admin:check</code>, <code>./hydra make:source invoice --writable</code> &mdash; and resolves its own directory, so it works from anywhere in the project.</p>

<h3>Three new documentation pages</h3>

<p><a href="/docs/validation.html">Validation</a>, <a href="/docs/database.html">the database</a> and <a href="/docs/auth.html">authentication</a> are documented for the first time. The auth page exists because the framework ships two contracts it never fills &mdash; <code>AuthenticatableInterface</code> and <code>UserProviderInterface</code> &mdash; so auth does not work until an application binds a provider, and nothing on the site said so.</p>

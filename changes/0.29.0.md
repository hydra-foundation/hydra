Hydra reads content kept in files. A directory of Markdown posts with front matter is now something both halves of a site can read: `ContentDirectory` lists the posts and renders one for a public page, and `ContentSource` puts the same directory in the admin as a module, listed, searched, sorted and filtered like a table, read only, because the files live in git and change there. A post whose front matter is broken is listed with the reason rather than hiding the others. It is the second piece of the website's blog.

It is 0.29.0 because `view` and `admin` gain API, and `MarkdownInterface` gains a method: a class of your own implementing it needs `frontMatter()`. `CommonMarkRenderer` has it, so an app using it changes nothing.

## Upgrading

- **Views:** A class of your own implementing `MarkdownInterface` needs the new method. `CommonMarkRenderer` has it.

## Views

- `MarkdownInterface` gains `frontMatter(string $source): array`: a content file's front matter without rendering its body, so a page listing a directory of posts costs no Markdown. It throws the same `InvalidFrontMatter` as `parse()` and reads the same block, so a list and a page never disagree about where the front matter ends.
- `Hydra\View\Content\ContentDirectory` reads a directory of Markdown files with front matter, such as a blog's posts kept in git. `all()` lists every `*.md` whose name is a slug (`[a-z0-9-]+`), by slug, reading front matter only; `find($slug)` reads one, and anything that isn't a slug never reaches the disk; `document($file, trusted: true)` renders it. Each `ContentFile` carries its slug, path, modified time, front matter and body source. A file whose front matter won't parse is still listed, with empty meta and the reason in `error`, so one bad post never hides the rest. A directory that doesn't exist throws, naming the path.

## Admin

- `Hydra\Admin\Sources\ContentSource` lists a `ContentDirectory` in the admin, declared like a `TableSource`: `columns`, `sortable`, `searchable`, `filterable`, `defaultSort`. A row is a file's front matter plus `id` and `slug`, `body`, `modified_at` and `problem`, which every row has without declaring. Search, sort (dates and numbers as such, text naturally, ties by slug), filters and day ranges all run in memory; a list column such as `tags` matches a filter when it contains the value. `map:` adds the columns a site derives, such as a post's status, and sees dates and lists as they were read; a row is flattened for printing after it, dates to ISO 8601 and lists joined with ", ". A file whose front matter won't parse is listed with the reason in `problem`. Read only, and `admin:check` checks a module over it like any other.

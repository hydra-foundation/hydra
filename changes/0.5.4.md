<p>The skeleton&rsquo;s audit module was built by hand against <a href="/docs/module.html">the checklist</a> rather than generated, deliberately, to find out what writing one is actually like. It found three things: a pile of duplication worth abstracting, an event carrying too little to audit, and an htmx trigger that had never fired. Framework suite 1129 tests and 2213 assertions to 1206 and 2544; the skeleton 203 and 613 to 300 and 897.</p>

<h3>TableSource</h3>

<p><a href="/docs/admin.html#sources"><code>Hydra\Admin\Sources\TableSource</code></a> is the read side of one table, declared rather than written. <code>page()</code> and <code>find()</code> exist once, over <code>table</code>, <code>columns</code>, <code>sortable</code>, <code>searchable</code>, <code>filterable</code> and <code>defaultSort</code>. The three sources in the skeleton went from 366 lines to 192.</p>

<p>It is not <code>final</code>, and <code>$db</code> and <code>$table</code> are protected, because a module adding the write contracts writes its own SQL against the table it already declared. <code>conditions()</code> is the override point for a join or a filter that is not equality: the short way, not the only way. <code>UserSource</code> is the proof &mdash; it extends this for the read side and keeps its own create, update and delete, where what a blank password means and who may not be deleted are facts about the table rather than boilerplate.</p>

<p>A malformed declaration is refused where the source is constructed rather than on the request that would have run the SQL: a non-identifier table or column name, an empty column list, or any of the four lists naming a column the source does not read.</p>

<div class="note warn">
  <span class="label">The check that earned the class</span>
  <p>A filter key the source does not select builds no clause at all, so the screen answers a narrowed request with the <em>whole table</em>, unfiltered and unremarked. It happened three separate times while writing one source by hand, and nothing in the framework, the test suite or the static analyser would have said a word. What <code>TableSource</code> still cannot check is the module&rsquo;s own pairing: a <code>-&gt;filterable()</code> field on a key the source does not list is the same silent widening, one file over. That one needs a test per module.</p>
</div>

<h3>RowDeleted carries the row it removed</h3>

<p>A minor&rsquo;s worth of API, taken as a patch because nothing was removed. <code>RowUpdated</code> already carried the row as it stood, because afterwards nobody can reconstruct it; for a delete that holds more strongly &mdash; an updated row can still be read and a deleted one cannot &mdash; and the event was announcing an id and nothing else.</p>

<p><code>AdminController::destroy()</code> now reads before the write lands. The read is skipped when no dispatcher is bound, so a module nobody listens to does not pay a lookup on every delete, and the payload is empty when the source implements no <code>RowSourceInterface</code>. The event is still announced in that case: the row still went.</p>

<h3>The admin&rsquo;s live search had never fired</h3>

<p>The filter partial carried <code>hx-trigger="submit, change, keyup changed delay:300ms"</code>. In htmx&nbsp;4 <code>changed</code> compares against the element the trigger is <em>on</em>, and on a form that is permanently inert &mdash; measured zero requests for typing and for clearing alike.</p>

<p>The reported symptom was only the visible corner of it: clearing with the &times; needed a blur before the table updated, because <code>change</code> still fired on blur and had been covering for the rest. It is <code>input from:#admin-search changed delay:300ms</code> now.</p>

<h3>The skeleton&rsquo;s audit module</h3>

<p>The feature all of the above came out of. It is application code rather than framework code, and the parts worth carrying forward are the ones about the seam between them.</p>

<dl class="defs">
  <dt>The column is <code>module</code>, not <code>table_name</code></dt>
  <dd>What the admin announces is a module slug, and the two only coincide by accident. A column named for a table that nothing ever looks a table up by is a collision waiting to be believed. <code>username</code> is denormalised alongside <code>user_id</code>, because the foreign key is <code>ON DELETE SET NULL</code> and deleting an account would otherwise erase who made every change it ever made.</dd>

  <dt>The repository clips to the column widths</dt>
  <dd>SQLite stores an over-long <code>VARCHAR</code> without complaint and MariaDB in strict mode refuses the insert, so this is the one thing a SQLite-only suite structurally cannot catch &mdash; hence a test per width, and one proving the cut counts characters rather than bytes.</dd>

  <dt>A listener, not a service called by hand</dt>
  <dd>The admin already emits the events and <code>boot()</code> already subscribes to the base class, so no module has to remember to record anything. It is registered as a closure rather than an instance: <code>boot()</code> runs before anything rebinds <code>ConnectionInterface</code> and every integration harness rebinds one immediately after, so an instance built at boot would go on writing to whichever database was bound then.</dd>

  <dt>Values come from an allowlist per module</dt>
  <dd>Never a blocklist of secrets. The users module declares a password input, so the values on the event carry one in plain text; the two failure directions are &ldquo;a field nobody listed goes unrecorded&rdquo; and &ldquo;a secret nobody listed gets written down&rdquo;, and only one of those is survivable.</dd>

  <dt>A write-only field reads as changed on every edit</dt>
  <dd><code>RowUpdated::changed()</code> has nothing to compare against, because the source never reads the field back. Left alone, every user edit would have been recorded as a password change, which is the same as recording none. The listener re-applies the form&rsquo;s own rule: blank means leave it alone.</dd>

  <dt>An export is audited, under the reserved row id <code>export</code></dt>
  <dd>It names no row, but it is the one admin action that takes a whole table at once, and a trail recording every single-row edit and not that is missing the largest thing that ever happens to the data.</dd>
</dl>

<p>Two hand-kept lists ship with it and both fail quietly: the listener&rsquo;s <code>AUDITED</code> needs a line each time a module becomes writable, and the module&rsquo;s own <code>MODULES</code> needs one each time a module can announce anything. The first records bare &ldquo;something happened&rdquo; rows without it; the second only loses the filter, and still lists under the raw slug.</p>

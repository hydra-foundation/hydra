<p>Until now, the admin could only take strings. A module can now declare a file control the way it declares a text box, and the admin receives the upload, checks it, stores it, and cleans up the old file. A new package, <code>hydrakit/filesystem</code>, stores the files. The skeleton&rsquo;s first use of it is a picture for every user.</p>

<p>Everything here is new, so this is a patch.</p>

<h3>Upgrading</h3>

<p>The admin now requires <code>hydrakit/filesystem</code>, and <code>hydrakit/filesystem</code> and <code>hydrakit/validation</code> both require <code>ext-fileinfo</code>. A module with no file controls works as before, with no disks registered. A module that declares one without disks registered fails with an error naming <code>FilesystemServiceProvider</code>.</p>

<p>To take uploads in an application built on the skeleton:</p>

<ul>
  <li>Register <code>FilesystemServiceProvider</code> in <code>Bootstrap</code> with the storage and document-root paths, and add <code>storage:link</code> to <code>bin/console</code>.</li>
  <li>Run <code>chmod 1777 storage/uploads storage/public &amp;&amp; ./hydra storage:link</code> once outside <code>./bin/dev</code>, which now does both itself. PHP&#8209;FPM writes the uploads as <code>www-data</code>.</li>
  <li>Copy the <code>location ^~ /storage/</code> block into your nginx config and reload it. It serves the public disk with <code>nosniff</code>, a <code>sandbox</code> CSP, and a cache that never expires.</li>
</ul>

<p>To get avatars too, run the new migration (it adds <code>users.avatar</code>), then copy <code>src/Admin/Avatar.php</code>, <code>src/View/Avatars.php</code>, <code>views/partials/account.php</code> and the avatar changes to <code>User</code>, <code>UserRepository</code>, <code>UserSource</code>, <code>UsersModule</code>, <code>SettingsController</code>, <code>AccountPresenter</code> and the account settings view.</p>

<h3>The filesystem</h3>

<ul>
  <li><code>StorageInterface</code> stores a stream under a key it picks itself: the directory, 32 random hex characters, and an extension for the type found in the bytes. The client&rsquo;s filename and extension are never used, so an upload named <code>shell.php</code> is stored as whatever it really is, and PHP source is stored as <code>.bin</code>.</li>
  <li>A key that would reach outside the disk is refused by every method, with <code>InvalidKey</code>. A key with no file behind it throws <code>FileNotFound</code>.</li>
  <li>There are two disks. The private one, <code>storage/uploads</code>, is never served by the web server. The public one, <code>storage/public</code>, is served through a <code>public/storage</code> link. Only the public disk has <code>PublicStorageInterface::url()</code>, and <code>StorageInterface</code> resolves to the private disk.</li>
  <li><code>Disks</code> holds both. A column stores a qualified key such as <code>private:avatars/&hellip;.png</code>, so whatever reads it knows which disk the file is on. <code>FILESYSTEM_PUBLIC_URL</code> points the public disk at another host.</li>
  <li><code>storage:link</code> creates a relative link, so it works both in the containers and on the host. It does nothing if the link is already there, and never replaces a directory or a link to somewhere else.</li>
  <li><code>StorageContractTestCase</code> holds any other driver, an object store say, to the same rules.</li>
</ul>

<h3>Validation</h3>

<ul>
  <li><code>UploadedFile</code> turns each of PHP&rsquo;s upload errors into a sentence. <code>MaxFileSize</code> measures the stream, not the size the request claimed. <code>MimeType</code> reads the type from the bytes with <code>finfo</code> and ignores the type the client sent.</li>
  <li>A file input left empty counts as missing, so <code>Nullable</code> skips it and <code>Required</code> refuses it.</li>
</ul>

<h3>The admin</h3>

<ul>
  <li><code>Input::file()</code>, with <code>storedIn()</code>, <code>accepts()</code>, <code>maxSize()</code> and <code>removable()</code>. A form holding a file control is posted as multipart, by the browser and by htmx.</li>
  <li>The source never sees an upload. It gets the stored key, or <code>null</code> when the file is removed, or no key at all when the input was left empty, which keeps the stored file.</li>
  <li>A new file is deleted if the source refuses the write. The old file is deleted once a replace or a remove has saved, and a deleted row takes its files with it.</li>
  <li><code>GET /admin/files?key=&hellip;</code> serves a private file to anyone signed in. Only JPEG, PNG, GIF, WebP and AVIF are shown inline; everything else, SVG included, is a download.</li>
  <li><code>Field::image()</code> shows a stored file as a thumbnail in the list and a larger picture on the row screen. It exports as the key, and shows <code>fallbackIcon()</code> when there is no file. The edit form previews the stored picture.</li>
  <li>The shell takes an <code>account</code> slot, which the application fills with who is signed in. It is shown at the right of the top bar on a narrow screen and above Sign out on a wide one.</li>
</ul>

<h3>Testing</h3>

<ul>
  <li><code>Client::withFiles()</code> sends files with a post, the way a multipart form does.</li>
</ul>

<h3>The skeleton</h3>

<ul>
  <li>Every user can have an avatar: JPEG, PNG, WebP or GIF, up to 2&nbsp;MB, stored on the private disk.</li>
  <li>An admin sets or clears it in Users, which also shows it in the list and on the user&rsquo;s screen. Anyone signed in sets or removes their own under Settings &rarr; Account.</li>
  <li>The admin shows the signed-in user&rsquo;s picture and name, linking to their account. A user with no picture gets a person icon.</li>
</ul>

<p>Changing a password used to leave every other session on the account signed in, including one belonging to whoever the change was meant to lock out. The guard now signs those sessions out. <code>GuardInterface</code> gains a method to make that possible, and a guard written against <code>^0.8</code> no longer satisfies the interface. That is why this is 0.9.0. Composer will not install it until you widen the constraint to <code>^0.9</code>.</p>

<h3>Upgrading</h3>

<p>A guard of your own needs a <code>refresh(AuthenticatableInterface $user): void</code>. Anything that changes the signed-in user&rsquo;s own password should call <code>$guard-&gt;refresh($user)</code> with the reloaded user afterwards, or it signs itself out on the next request.</p>

<div class="note warn">
  <span class="label">Everyone signs in once more</span>
  <p>A session opened before the upgrade carries no password stamp and is treated as stale. Every signed-in user lands on the login page on their first request after deploy.</p>
</div>

<h3>The session knows which password it was opened with</h3>

<p><code>SessionGuard::login()</code> stores a digest of the password hash beside the user id, the same digest a reset link carries. <code>user()</code> compares it on every request against the hash it has just loaded, so the check costs no extra query. A mismatch clears the whole session, the way <code>logout()</code> does. A reset, an admin setting somebody&rsquo;s password and a change from another browser all end the account&rsquo;s other sessions. <code>refresh()</code> keeps the session that made the change: it moves the session id and stores the new digest, and dispatches nothing, because nobody signed in. <code>FakeGuard</code> implements it and <code>GuardContractTestCase</code> checks it. <a href="/docs/auth.html#guard">Authentication</a> has the details.</p>

<h3>In the skeleton</h3>

<p>Settings has an Account category where the signed-in user changes their own password. It asks for the current one. Checks of it are limited to five an hour per account, and a typo in the confirmation does not use one up. A change writes an audit row, <code>account.password_changed</code>, filed with the account&rsquo;s other audit rows and holding no values. An admin who sets their own password through Users stays signed in too. Changing your own address waits for a queue, because the notice to the old address should not be sent inside the request.</p>

<p>Until now an installation had no way to learn that a newer Hydra existed short of someone reading this page. The admin now checks, twice a day, and says so on the System Health dashboard and in its footer, louder when what was missed is a security fix. <code>hydra:upgrade</code> is how to act on it. This is the first release the feed announces, so 0.9.8 is the first version that can be told about the next one.</p>

<p>Every symbol here is new, so this is a patch. The one shared template that changed, <code>admin/partials/widget-health</code>, takes an optional <code>link</code> it did not take before, and a card that passes none renders as it did.</p>

<h3>Upgrading</h3>

<p>Nothing is required, and nothing happens until you declare the card. To take what the skeleton did: add an <code>UpdatesWidget</code> card to a dashboard, pass <code>UpdateCheck</code> to the admin layout as <code>updates</code> and render <code>admin/partials/update-notice</code> after the version in its footer, and register <code>UpgradeCommand</code> in <code>bin/console</code> with the project root. To opt out of the fetch, set <code>HYDRA_UPDATE_CHECK=false</code>. <a href="/docs/admin.html#health">Health cards</a> and <a href="/docs/console.html#hydra-upgrade">hydra:upgrade</a> have the details.</p>

<h3>The release feed</h3>

<p><code>/version.json</code> on this site names the latest release, the newest in each series and every release that was a security fix. <code>release.sh</code> writes it once Packagist has the tag, and not before, or every installation would be told to upgrade to something Composer cannot find yet. <code>--security</code> marks a release as a fix. The file is merged rather than rewritten, since the security list is history: an installation three patches behind still has to learn it skipped one.</p>

<h3>UpdateCheck</h3>

<p><code>UpdateCheck</code> reads the feed through <code>ReleaseFeedInterface</code> and compares it with the installed version. <code>HttpReleaseFeed</code> is a plain GET that sends nothing about the installation, gives up after two seconds and reads at most 64&nbsp;KB. The answer is cached for twelve hours. A failure is cached for one, so a host with no route out pays the timeout once an hour rather than on every admin page, and a cache that will not answer skips the fetch entirely rather than fetching on every page. A newer release in the installed series is a patch, flagged as a security fix only when a fix falls between the installed version and that one. A newer series is reported separately, because <code>^0.9</code> never resolves to <code>0.10</code>. A checkout that is not on a tagged release is not compared. <code>FakeReleaseFeed</code> is the fake.</p>

<h3>UpdatesWidget</h3>

<p>The card: green when current, amber for a patch or a new series, red for a security fix, with a link to that release&rsquo;s notes here. The skeleton puts it on System Health, and its admin footer adds &ldquo;0.9.9 available&rdquo; beside the version when there is one. The sign-in page never shows it.</p>

<h3>hydra:upgrade</h3>

<p>Runs <code>composer update "hydrakit/*"</code>, and if anything moved, <code>migrate:run</code> and <code>route:cache:clear</code>, each in a new process, since the running one still has the old framework loaded. It prints what moved from what to what. It is for a development checkout, whose lock is what gets deployed, and it refuses one whose <code>vendor/hydrakit</code> is symlinked to a local framework before Composer can replace the links with copies of the last tag. It does not stop you running it in production; it just is not meant for it.</p>

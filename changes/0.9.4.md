<p>0.8.1 left three things for the queue: auth events for the reset and verification flows, a verification link nobody has to ask for, and a warning to the address an account used to have. The queue arrived in 0.9.2, and all three are here. So is the other half of the Account screen: a user can now change their own address, and it moves only once the new inbox has been reached. The framework gains classes, events and one optional parameter, and nothing published was removed or narrowed, so this is a patch.</p>

<h3>Upgrading</h3>

<p>Nothing is required. <strong>Links sent before the upgrade stop working</strong>: <code>SignedToken</code> has one more field, so a reset or verification link minted by 0.9.3 no longer opens. They last an hour and a day, and whoever holds one can ask for another. To log the new events, register <code>LogAuthEventsListener</code>&rsquo;s three new handlers the way the skeleton&rsquo;s <code>AppServiceProvider</code> does.</p>

<h3>A token that carries a value</h3>

<p><code>SignedToken::mint()</code> takes an optional fifth argument, <code>$carry</code>. <code>TokenClaims</code> returns it as <code>$carried</code>. Unlike the bound value, which travels as a digest, a carried value can be read by anyone holding the link; the signature only stops it being changed. <code>EmailChangeTokens</code> is built on it. It carries the address an account wants to move to and resolves to an <code>EmailChange</code> with the user and that address. It is bound to the current address, so the move spends it, and to the password hash, so an owner who changes their password cancels a move they did not ask for. <a href="/docs/auth.html#links">Reset, verification and address-change links</a> has the table.</p>

<h3>Three more auth events</h3>

<p><code>PasswordResetLinkSent</code>, <code>PasswordReset</code> and <code>EmailVerified</code>, each carrying the user, and a handler for each on <code>LogAuthEventsListener</code>. The guard does not dispatch them, because these flows are the application&rsquo;s. <code>PasswordResetLinkSent</code> belongs where the mail is actually sent: an event on request would record the unknown addresses the form takes care not to reveal. A password reset logs at <code>notice</code>, one level above a sign-in, because a credential changed.</p>

<h3>In the skeleton</h3>

<p>The Account screen has a second form, for a new address and the current password. The link goes to the new address, and the account keeps the old one until it is opened; the new address then counts as verified. An address another account took in the meantime is refused. Both forms spend one budget of five password checks an hour. When an address moves, from Settings or from the Users module, the old address is sent a mail naming the new one. It says to contact an administrator rather than to reset, since a reset would now go to the new address. The Users module sends a verification link when it creates an account or changes an address, from a listener on the admin&rsquo;s write events rather than from inside <code>UserSource</code>. The reset job, the reset form and the verify link dispatch the three new events. Change links are on the activity log&rsquo;s ignore list with the other two.</p>

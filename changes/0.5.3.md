<p>Two features that turned out to be one. An export is the single admin action that hands over a whole table at once, which makes it the thing anything watching the admin most needs told about &mdash; so <a href="/docs/admin.html#export">the screen</a> and <a href="/docs/admin.html#events">the events that announce it</a> shipped together.</p>

<h3>The list as a file</h3>

<p><code>ExportScreen</code> writes every row the current filters, search and order match, for the fields declared on <code>Surface::Export</code>. It is declared and never inferred, unlike the list screen a module with a source and fields gets for free: an export hands a whole table to whoever can open it, past the pagination that otherwise bounds what one request costs, so it is a decision a module makes rather than one it inherits. <code>requires()</code> is there for the same reason &mdash; the ability to read a page of something is not obviously the ability to walk out with all of it.</p>

<dl class="defs">
  <dt><code>Extractor</code></dt>
  <dd>The one thing that knows how to walk a source that only answers in pages. It yields rather than collects, so what a caller does with a row is over before the next one is read and the source&rsquo;s own page size is the only slice ever held. 500 rows a read, 50,000 rows a cap &mdash; the same blast-radius reasoning as <code>Criteria::MAX_PAGE</code>. <code>Criteria::inPagesOf()</code> is what re-sizes the bite without touching the view.</dd>

  <dt><code>Csv</code></dt>
  <dd>RFC&nbsp;4180 shaped, and safe to open. A spreadsheet is not an inert viewer &mdash; it evaluates a cell beginning with <code>=</code>, <code>+</code>, <code>-</code> or <code>@</code>, and the rows an admin exports are usually the ones strangers wrote. Guarding that belongs here and not at the call site, because a caller only forgets once. A byte-order mark goes on the front: every reader tolerates it and Excel is the one that needs it, or a UTF-8 export of anything but ASCII opens as mojibake.</dd>

  <dt><code>Surface::Export</code></dt>
  <dd>Its own surface, because a spreadsheet is not a table: a column too wide to sit in a row still belongs in the export, and a formatter written for a cell &mdash; &ldquo;3 minutes ago&rdquo;, a badge &mdash; is the wrong thing to put in one. A declared field is on it by default, since the alternative is an export that silently ships fewer columns than the module declared.</dd>

  <dt><code>Responder::download()</code></dt>
  <dd>A body the browser saves rather than renders. Both spellings of the name are sent: the quoted one carries only characters a header can hold literally, because a filename is attacker-influenced often enough &mdash; a row&rsquo;s title, a module&rsquo;s slug &mdash; that the quote and the newline inside it are worth spending a transliteration on, and <code>filename*</code> carries the name as written for every current client.</dd>
</dl>

<h3>Admin events</h3>

<p><code>RowCreated</code>, <code>RowUpdated</code>, <code>RowDeleted</code> and <code>Exported</code>, all deriving from one <code>AdminEvent</code>. The dispatcher matches a listener against an event&rsquo;s supertypes, so a single registration against the base class hears everything the admin will ever announce, including whatever is added to it later. <code>LogAdminEventsListener</code> is the one the package ships.</p>

<div class="note">
  <span class="label">No event carries who did it</span>
  <p>The admin knows what a screen may be reached <em>with</em> &mdash; an ability &mdash; and not who reached it. Reaching for the guard here would make an audit trail&rsquo;s worth of coupling out of a package that does not otherwise depend on authentication at all. A listener runs inside the request and can ask. For the same reason a written row&rsquo;s values are on the event but not in <code>context()</code>: a module&rsquo;s fields are whatever the application declared, and a listener logging them wholesale would copy a password into the log the first time somebody edited one.</p>
</div>

<p><code>AdminController</code> is registered by hand in <code>AdminServiceProvider</code> rather than autowired, and the reason is sharp enough to be worth repeating: PHP&#8209;DI skips optional constructor parameters entirely, so a dispatcher appended to the signature with a default would arrive null in every application, including the ones that had bound one. The admin would announce nothing and nothing would say why.</p>
